# 404 page design

## Goal

Replace the plain-text fallback for every unmatched request with the specified
themed HTML 404 page while preserving the HTTP 404 status. This includes
unknown browser routes, unknown API routes, and unmatched non-GET requests.

## Architecture

- Add `public/404.html` as a standalone document. It uses the existing global
  stylesheet, shared theme bootstrap script, and `data-mode="404"`.
- Add a small page-specific module that initializes only the theme toggle. The
  answer-page module remains exclusive to the question pages.
- Load the 404 template once when the Express app is created. The final fallback
  middleware sends it with status 404 and an HTML content type for every method
  and unmatched path.

## UI and behavior

- The document follows the supplied layout: shared card and header; a `404`
  error code; the “Page not found” heading; a ruled navigation section linking
  to `/yes`, `/no`, and `/random`.
- The page uses the established light and dark theme tokens. The saved theme
  preference is applied before styles load, and the toggle updates both
  `data-theme` and local storage.
- The 404 document does not load answer, form, sharing, or autoplay behavior.

## Testing

- Server tests verify status 404, HTML content type, and the expected 404
  markup for an unknown browser path, an unknown API path, and unmatched
  non-GET requests.
- Browser tests verify navigation links and theme-toggle persistence on the
  404 page.
